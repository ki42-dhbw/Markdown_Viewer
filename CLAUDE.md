# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A local Markdown/Jupyter-notebook viewer for Windows, distributed as a single `.exe`. There are **two independent implementations** of the same product — they do not share code:

- **`Markdown_Viewer_webapp.py` / `Markdown_Viewer_webapp_01.py`** — the *current* approach. A tiny Python `http.server` on `127.0.0.1:8742` that serves one self-contained HTML page and auto-opens the browser. All rendering happens client-side in JavaScript (`marked.js` + `MathJax`, loaded from jsDelivr CDN). This is what gets built into the shipped executable.
- **`Markdown_Viewer_v01.py`** — an earlier, standalone Tkinter desktop app that parses Markdown with hand-written regex and renders into a `tk.Text` widget using tag styling. No server, no browser, no external assets. Kept as an alternative; not part of the build.

`_webapp_01.py` is the newer webapp variant and the **current build entry point** (`MarkdownViewer.spec` now points at it). It differs from `_webapp.py` by adding **content-based notebook detection** (`looksLikeNotebook` — sniffs JSON for `cell_type`/`nbformat` so `.ipynb` content renders correctly even without the extension), **no-cache HTTP headers**, **PDF export** (an "Als PDF" toolbar button → `saveAsPdf()` → `window.print()`, styled via an `@media print` block), and **Screenshots, Text & Dokumente → Markdown** (see the architecture notes below). `_webapp.py` is the older variant and lacks these; keep both in sync only if you intentionally maintain the older one.

The viewer itself stays fully offline, and so does the **default** conversion engine (Windows OCR via PowerShell) and the whole rich-paste/.docx path. Two things reach the network, both only on an explicit user action: the optional Claude-API engine, and downloading images that pasted content merely links to — the latter gated behind a checkbox that is off by default.

UI text, comments, and dropzone labels are in **German** — match that when editing user-facing strings.

## Build

The shipped artifact is `dist/MarkdownViewer.exe`, built with PyInstaller (one-file, windowed/no-console) from `Markdown_Viewer_webapp_01.py`:

```powershell
python -m PyInstaller --onefile --noconsole --name "MarkdownViewer" Markdown_Viewer_webapp_01.py --noconfirm
```

Or via the committed spec: `python -m PyInstaller MarkdownViewer.spec` (the spec already targets `_webapp_01.py`). Both `build/` and `dist/` are generated output.

There are **no tests, no linter, and no dependency manifest** — the app uses only the Python standard library (`http.server`, `tkinter`, `urllib.request`, `subprocess`, `json`, `re`, etc.). Nothing to `pip install`. Two decisions keep it that way, and both are deliberate: the Anthropic API is called over raw `urllib.request` instead of the `anthropic` SDK, and the local OCR goes through `powershell.exe` instead of a WinRT binding package (`winsdk`/`winrt`). Do not swap either one in without deciding to give the zero-dependency invariant up.

Note that `_webapp_01.py` now imports `tkinter` (lazily, inside `ask_save_path()`) for the native save dialog, so the PyInstaller build pulls in Tk.

## Run during development

```powershell
python Markdown_Viewer_webapp_01.py   # starts server, opens browser; Ctrl+C to stop
python Markdown_Viewer_v01.py         # launches the Tkinter desktop version
.\start.bat                           # convenience launcher for the webapp
```

`start.bat` runs `_webapp_01.py` via whichever Python it can locate (`py` → `python` → `C:\Python313\python.exe`) — the intended way to launch the viewer without the built `.exe`.

The conversion feature runs **without an API key** on the local Windows-OCR engine. Only the optional Claude-API engine needs a key in the environment before launch — when one is set, the UI defaults to it:

```powershell
$env:ANTHROPIC_API_KEY = "sk-ant-..."
```

`Testdaten/` and `dist/*.md` hold sample Markdown/notebook files for manual verification. There is no fixture for the rich-paste path — it depends on real clipboard data, so verify it by actually copying from a browser and from Word.

## Architecture notes for the webapp

The entire frontend is a single `HTML = r"""..."""` string constant inside the Python file — HTML, CSS, and JS all live in that one raw-string. Editing the UI means editing that string; there is no separate asset pipeline.

Key JS rendering flow: `dispatchRender()` decides Markdown vs. notebook → `renderMarkdown()` (via `marked.parse`) or `renderNotebook()` (walks `nb.cells`, dispatches each output through `renderOutput()`). Notebook HTML/SVG outputs pass through `sanitizeHtml()`, a minimal DOM-based sanitizer that strips `<script>`/`<iframe>`/`on*` handlers and `javascript:` URLs — preserve this when touching output rendering, since notebook `text/html` output is otherwise untrusted.

The server is a `ThreadingServer` (`ThreadingMixIn` + `HTTPServer`) speaking HTTP/1.1, so a running conversion no longer blocks the page. It exposes nine routes: `POST /api/hello` / `POST /api/bye` (page lifetime, see below), `GET /` (the HTML page), `GET /api/file?path=...` (reads a local file, returns `{content, name, size}` as JSON; assumes UTF-8), `GET /api/status` (`{local_ocr, has_key, model}` — what the client uses to pick the default engine and word its hints), `POST /api/fetch-image` and `POST /api/import` for pasted/imported mixed content, and `POST /api/convert` / `POST /api/save` for the conversion feature.

**Screenshots, Text & Dokumente → Markdown** (toolbar button "Screenshots/Text") turns pasted/dropped screenshots, pasted text, **pasted rich content** (formatting and images intact) and **.docx/.html files** into one Markdown document. Two interchangeable engines produce that Markdown, picked per conversion in the `#engineSelect` dropdown:

- **`local` (default without a key)** — no key, no network, no extra package. Images go through the Windows OCR engine (`Windows.Media.Ocr`), driven by a PowerShell 5.1 script (`OCR_PS`) that is handed to `powershell.exe -EncodedCommand` (UTF-16LE base64; the image path travels in the `MDV_OCR_IMAGE` env var, so no quoting problems). `CREATE_NO_WINDOW` matters — the app is built `--noconsole` and would otherwise flash a console. Pasted text skips OCR entirely and only runs the local formatter.
- **`api`** — the Anthropic Messages API, `CLAUDE_MODEL` (`claude-opus-5`), key from `ANTHROPIC_API_KEY`, never written to the file. Structure recognition (especially tables) is clearly better; this is the default when a key is present.

`GET /api/status` reports `{local_ocr, has_key, model}`; `loadServerStatus()` picks the default engine from it and words the hint under the toolbar. `_handle_convert` treats **anything but `engine: "api"` as local** — an old client, or a missing field, must never silently hit the network.

- The client keeps a `shots[]` array of three kinds, distinguished by `kind`: `'image'` (`dataUrl`, `mediaType`, `file`, `width`, `height`) fed by `addShotFiles()`, `'text'` (`text`) fed by `addShotText()`, and `'rich'` (`template`, `images[]`) fed by `addRich()`. All share `name`, `markdown`, `truncated`, `error`, and all flow through the same conversion loop, list rendering, reordering and document assembly.
- **A textarea silently destroys rich content**, and that trap is worth remembering: the panel's `#textInput` invites a paste, but a textarea can only hold plain text, so images and formatting were lost before anything of ours ran. It therefore has its own `paste` listener that intercepts and routes to `addRich()` — the general `isEditable()` bail-out would otherwise hand the paste to the field. The same applies to any input you add later.
- Whether a paste takes the HTML or the text route is decided by `isRichClipboard()`: real structure or images → HTML; merely styled text (web apps wrap even a single sentence in `<span style=…>`) → text route, where the formatter can still add structure. `addRich()` immediately reports how many images were found and, if some are remote and the checkbox is off, says so — otherwise the user only notices at conversion time.
- **"Einfügen" on the main page** (toolbar and dropzone) is the active counterpart to `Strg+V`: `pasteFromClipboard()` reads the clipboard itself via `navigator.clipboard.read()` — which needs a user gesture, a secure context (localhost counts) and a one-time browser permission, so both the missing-API and the denied-permission case fall back to telling the user to press `Strg+V`. It routes by what the main page is for: an image becomes a screenshot entry, rich HTML becomes a rich entry, and **plain text is rendered in the viewer** (`showPastedText()` → `dispatchRender()`), because looking at Markdown is the viewer's purpose. `Strg+V` deliberately keeps its old behaviour of collecting everything in the conversion panel.
- Content arrives through several paths, and the handlers try them **in order of fidelity**: image files → `text/html` → `text/plain`. `Strg+V` outside an input, dragging a selection or file onto either dropzone, the panel's `#textInput` box plus "Text übernehmen" (`Strg+Enter`), the file pickers, and the main viewer dropzone all funnel into the same three intake functions. The paste and drop handlers bail out via `isEditable()` when the target is an input/textarea — otherwise pasting into the editor or the text box would also queue a new entry.
- **Image filenames are assigned once and never renumbered** (`shotSeq`/`embedSeq` → `screenshot-N.ext` / `bild-N.ext`). They are baked into converted Markdown that the user may already have edited, so a positional scheme would break the links on every reorder or delete. Gaps after a deletion are the accepted price; the counters reset only when the whole area is cleared. `allImages()` is the single place that pairs a `dataUrl` with its filename — `previewShots()` and `saveShots()` both go through it.
- Section headings are positional (`ordinalOf()` counts per kind: "Screenshot 2", "Textabschnitt 1", "Inhalt 3") and independent of those filenames. **Rich entries get no synthetic heading at all** — they bring their own `#`/`##` structure from the source, and prefixing it would only add noise.
- **`POST /api/convert` handles exactly one image tile or one text chunk.** The client loops itself, which is what makes progress, cancel, and partial results possible: if entry 3 of 5 fails, the other four keep their text and only the failed one is retried (`↻` per row). A second click on "umwandeln" skips anything already done.
- **Tall screenshots are tiled, not shrunk.** `planTiles()` is engine-aware: for `api` it caps width at `MAX_API_WIDTH` (1568) and slices anything taller than `MAX_TILE_HEIGHT` (1200); for `local` it never downscales at all (that would cost OCR accuracy) and only slices at `MAX_LOCAL_TILE_HEIGHT` (4000) to stay inside the Windows engine's size limit. Without this a 1600×20000 full-page capture would scale down to ~566px wide and the text would be unreadable. Tiles are cut in original coordinates so no rounding gap appears at the seams; there is deliberately no overlap, so a line may split across a seam.
- Long text is chunked the same way by `splitText()` at `MAX_TEXT_CHARS` (12000), preferring paragraph, then line, then word boundaries. Chunks are joined with blank lines, like tiles.
- `prepareForApi()` sends the downscaled/tiled copy, but `shots[i].dataUrl` keeps the **original**, which is what gets written to disk. Don't collapse these two.
- `buildCombinedMarkdown()` assembles one document, linking each image as `bilder/<file>` (text entries get no image line). That relative path is deliberately independent of the chosen `.md` filename, so nothing needs rewriting at save time. `previewShots()` swaps those paths for data-URLs so the preview renders before anything is on disk. `refreshEditor()` compares against `lastGenerated` and refuses to clobber the textarea once the user has edited it.
- `transcribe_image()` / `transcribe_text()` share `_extract_text()`: they retry `RETRY_CODES` (429/5xx/529) with exponential backoff, raise on `stop_reason == "refusal"`, and report `stop_reason == "max_tokens"` back as `truncated` so the UI can mark the section as possibly cut off. The local engine always returns `truncated=False` — it has no token limit.
- `POST /api/save` writes the edited Markdown (LF endings, explicit `newline="\n"`) and drops the originals into a `bilder/` subfolder beside it. Image filenames pass through `os.path.basename()` — keep that, it is what stops `../` in a filename from escaping the folder.

**Mixed content (text + images) is taken from the clipboard's `text/html`, not re-recognized.** When you copy from a browser, Word or Outlook, the clipboard carries a `text/html` flavour with the full formatting *and* the image references — so for this path nothing is guessed at all, and it is the highest-fidelity route into the app by a wide margin. `richFromHtml()` parses it with `DOMParser`, runs it through the existing `sanitizeHtml()` (pasted HTML is foreign markup — never skip this), and `htmlToMarkdown()` walks the DOM into Markdown: headings, nested lists, tables, bold/italic/strike, inline code, `<pre>`, blockquotes, links. Word's own list markup is handled separately — it emits list items as plain paragraphs carrying `mso-list` styles and a literal `·` in the text, caught by `looksLikeWordList()` + `WORD_BULLET_RE`.

- **Pages built as web apps paste surrounding chrome along with the content**, and that shaped several rules. `SKIP_TAGS`/`isSkipped()` drop buttons, SVG icons, form controls and `aria-hidden` nodes — a "Kopieren" button sits above practically every code block on documentation sites and would otherwise land inside the listing. **But a skipped branch containing an `<img>` is kept**: these UIs make images clickable by wrapping them in a `<button>`, and skipping the button threw the image away with it. That bug looked exactly like "the page has no images", which is why `richFromHtml()` now counts `<img` in the raw HTML and reports the difference as `lostImages` — a conversion that loses images must say so. The `<pre>` branch reads the inner `<code>` when there is one — web apps build the header, language label and copy button *inside* the `<pre>`, while `<code>` holds only the listing — then clones and strips `button`/`svg`, takes the fence language from `class="language-…"` (`codeLanguage()`), and drops a one-word block directly above the fence that *equals* that language. The page also sets `<meta name="referrer" content="no-referrer">`, because image CDNs reject requests carrying a foreign referrer and pasted content points at exactly those CDNs.
- **Rich entries are shown the moment they are pasted, the way Word does it** — no conversion step for display. That works because a browser renders `<img src="https://…">` fine (only *reading the bytes* is restricted, and that is what the server is for). `addRich()` therefore calls `assignLocalImages()` (images already in the browser — `data:` URIs, docx media — get a `bilder/…` filename right away, so the editor never fills up with base64), renders the Markdown with remote images still pointing at their original address, and refreshes editor and preview. Conversion of a rich entry then means only "fetch the remaining images", and `needsWork()` in `convertShots()` picks entries by that, not by an empty `markdown`.
- **Completing the document happens at save time**, which is the moment it actually matters: `saveShots()` finds images still living on the web (`pendingRemoteImages()`), asks once, and `downloadPendingImages()` fetches them with `allow_remote: true` — the confirmation *is* the consent, which is why it may bypass the checkbox. It rewrites the addresses **in the editor text** rather than regenerating it, so the user's own edits survive. Declining is a valid answer and leaves working web links in the file.
- Each `<img>` becomes a `{{IMG:n}}` placeholder in the entry's `template` plus an entry in `images[]`; identical `src` values share one entry, so a repeated image is fetched and stored once. An `<img>` whose address cannot be read is registered too, carrying an error — **never drop an image silently**, or it goes missing from the result with nobody noticing.
- **When images do not arrive, the cause is almost always what the source page put on the clipboard**, and that cannot be guessed from here. "Zwischenablage prüfen" (`diagnoseClipboard()` → `clipboardReport()`) arms the next paste to report instead of import: available flavours, `<img>`/`<picture>`/`<svg>`/`background-image` counts, the first image tags, and the start of the raw HTML. Reach for this before theorising — a page that paints its images as CSS backgrounds or canvases simply has no `<img>` to take, and then the only route is copying the image itself. `imageSource()` resolves lazy-loading patterns: when `src` is missing or a tiny inline placeholder, it falls back to `data-src`/`data-original`/`data-lazy-src`, then to the **last** `srcset` candidate (usually the largest), then to a `<source>` in an enclosing `<picture>`. `resolveRichImages()` does that at conversion: `data:` URIs are decoded in the browser, everything else goes to `POST /api/fetch-image`. **`file://` is the important case** — Word and Outlook paste images as links into `…/msohtmlclip1/…`, which the browser may not read but the local server can. `http(s)` is only fetched when the user ticks `#allowRemote` (default off, so the local engine stays genuinely offline); otherwise the image keeps its original URL in the Markdown, which beats a relative link to a file that was never written. `renderRichMarkdown()` substitutes the placeholders, and `shotState()` reports how many images stayed unresolved instead of silently dropping them.
- **`blob:` image URLs cannot be recovered by anyone** — they address the source page's own memory, so neither the server nor our page (a different origin) can read them, and modern web apps use them a lot. This is not a bug to fix but a limit to communicate: `fetch_image()` says so in plain German, and the affected row grows a **"+ Bilder"** button (`pickMissingImages()` / `fillMissingImages()`) that fills the open slots, in order of appearance, from images the user picks by hand. `resetShot()` must clear `img.error` too, otherwise ticking "externe Bilder laden" and hitting ↻ would skip exactly the images the user wants retried.
- **`.docx` import is server-side** (`import_docx()` / `_DocxReader`): a docx is a ZIP of XML, so `zipfile` + `xml.etree` cover it with no new dependency. It reads `styles.xml` for heading levels (matching the **style name** `heading N`, since a German Word writes styleIds like `berschrift1`), `numbering.xml` to tell bullets from numbered lists, and the rels file to resolve `a:blip`/`v:imagedata` into `word/media/*`. It returns Markdown with the **same `{{IMG:n}}` placeholders** plus the image bytes, so a Word file joins the identical client-side flow as a paste. EMF/WMF are reported as skipped rather than embedded — browsers cannot display them.
- The three Markdown builders (`ocr_rows_to_markdown`, `format_text_markdown`, `_DocxReader.read`) all end in `_join_blocks()`, mirrored on the JS side by `joinBlocks()`. It keeps list items tight and separates everything else with a blank line — the subtle part is that a switch between bullet and numbered at the same or shallower indent has to break the list, while a deeper indent must stay tight or the nesting collapses.

**The local engine reconstructs structure from geometry, not from understanding.** `_run_ocr()` returns one `(left, top, height, text)` tuple per recognized line, and `ocr_rows_to_markdown()` derives the document from that: a vertical gap larger than `0.6 ×` the median line height starts a new paragraph (so wrapped lines get merged back), and a line taller than `1.6 ×` / `1.3 ×` the median becomes `#` / `##`. Those ratios are measured on **glyph boxes**, so a heading without descenders measures barely taller than body text — hence the third rule: a only-slightly-taller line that stands alone between two paragraph breaks, is short and ends without punctuation becomes `###`. Retune these thresholds against real screenshots, not in the abstract. `format_text_markdown()` does the same job for pasted text without geometry (blank lines, bullet glyphs, `\t` columns → `_tab_table()`, standalone short lines → `##`); it is deliberately conservative — everything unrecognized stays a paragraph.

**Tk must only be touched from the main thread.** Since the server is threaded, `_handle_save` does not call `ask_save_path()` directly: it queues a request on `_dialog_requests` via `request_save_path()` and blocks on a reply queue, while `pump_dialogs()` — which is what `main()` runs instead of sleeping — opens the actual dialog on the main thread. If you add another native dialog, route it through the same queue.

**The server ends with the last open page, and there is only ever one of it.** The "window" is a browser tab, so the process has to be told when it is gone: each page generates a `CLIENT_ID` and `announce()`s `/api/hello` on `pageshow` and `/api/bye` on `pagehide` (via `sendBeacon`, which survives the unload). The server keeps the ids in `_clients`; when the set empties, `client_bye()` arms `_quit_at` and `pump_dialogs()` returns once `QUIT_GRACE` (5 s) has passed — the grace period is what lets F5 through, since a reload says bye, requests `/` (`page_requested()` disarms) and says hello again. **There is deliberately no heartbeat timeout**: browsers throttle and freeze background tabs, and a missed ping would pull the server out from under a tab that is still open. The price is that a crashed browser leaves the process running — which the next start then simply reuses. `main()` asks `viewer_running()` (a `GET /api/status` that must contain `local_ocr`) before binding and, if a viewer answers, only opens another browser tab and exits. `allow_reuse_address` is off on Windows for the same reason: there `SO_REUSEADDR` lets several processes listen on one port, so every extra start used to linger as a silent second instance.

**Clearing the view** — `clearScreen()` (toolbar "Löschen", `Strg+Umschalt+L`; `Strg+L` is browser-reserved) is mode-aware and splits into `clearViewer()` and `clearShotArea()`. Clearing the document view is non-destructive (the file is still on disk) so it happens without a prompt; clearing the screenshot area throws away converted text, so it asks first — and must also blank `#textInput`, not just the collection. Both refuse while `converting` is true. `clearViewer()` must reset `searchMatches`/`searchIndex`/`lastSearchTerm` — stale entries would point at removed DOM nodes — and must blank `fileInput.value`, otherwise re-picking the same file fires no `change` event. `clearShotArea()` also resets `shotSeq`/`embedSeq`, which is safe precisely because the Markdown referring to those filenames is discarded in the same step.

**PDF export** is browser-native, not server-side: `saveAsPdf()` clears search highlights and calls `window.print()`. An `@media print` CSS block (at the end of the `<style>`) hides the toolbar/TOC/status bar, switches the dark theme to a light print layout, and sets page-break rules (`break-after: avoid` for headings, `break-inside: avoid` for code/tables/images/notebook cells). No dependencies are added — the user picks "Save as PDF" in the browser print dialog. When touching print styling, keep this block in sync with any new rendered elements.
